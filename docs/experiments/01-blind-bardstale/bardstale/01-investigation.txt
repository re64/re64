⏺ Here is what I actually dealt with, grouped by kind. I've tried to be honest
  about which distinctions emerged from the material rather than from a
  textbook.

  1. Containers (disk images)

  - Examples: bardst-1.d64 ("CITY DISK"), bardst-2.d64 ("BARDS TALE").
  - Identity: the file itself, plus the BAM name/ID inside. The two are a pair
    by convention only — nothing in the images links them except the loader's
    disk prompts ("Insert DUNGEON disk").
  - Independent? Yes; standard layout, fully understood with d64.py alone.
  - Relationships: owns sectors → files; the game's file-number ranges map to
    disks (a fact I had to reconstruct from directories and store in
    btfiles.py).

  2. Physical storage units (sectors, chains, slack)

  - Examples: track/sector cells; the directory chain; the orphan chain
    (6,7)→…→(5,18); the 1541 format-fill pattern 4B 01 01…; the final-sector
    slack shared by ~35 $BB00 overlays; Applesoft BASIC text in map slack.
  - Identity: (image, track, sector). Slack has no identity of its own — it's
    "the bytes past the real end", which I had to define (via slack.py's
    majority template).
  - Independent? Sectors yes. Slack no: whether bytes are content or junk
    depended on comparing files with each other and on knowing the overlay
    format.
  - Relationships: sectors → files (ownership); slack → "duplicate-of /
    residue-of" other units. Slack produced false facts (phantom call targets
    $2004, stale text in NM10/NM16) until modelled.

  3. Files as the game sees them

  - Examples: NM00…NMF0, plus the two packed programs.
  - Identity: the file number in the name (NM+hex) — that's the key the loader
    uses, and it's the identity I ended up using everywhere, not the directory
    entry.
  - Independent? Only as byte blobs. Their meaning required the loader's address
    table (PRG headers lie), so a file's "real" identity is (number, real load
    address, disk).
  - Relationships: number ranges ↔ load page ($C000, $AE00, $B600, $BB00, $E000,
    $F800); disk membership; save/load paths (NM00/01/0A are the only writable
    ones); duplicates across disks (NM5E–82).

  4. Programs and their stages

  - Examples: packer stage 1 (LZ in the stack page), stage 2 (RLE $9F), $C000
    screen init, GAME_INIT, resident kernel, intro demo, Utilities (NM03).
  - Identity: entry point + memory range + the moment in the boot sequence.
    Stage 2 code only exists after stage 1 ran — an entity defined by execution
    state, not by a file.
  - Independent? The packer stages yes (self-contained); I understood them by
    execution, not reading. The intro yes. The resident kernel no — it is
    meaningless without overlays and data.
  - Relationships: produces (stage 1 → stage 2 → final image); entry chain $C000
    → $0800 → $08D2 → SET_MODE → $AE00.

  5. Memory regions / memory configurations

  - Examples: bitmap $2000, text window, party area $CB80+$80·n, PICBUF $C000
    (shared by pictures and roster and NM0A), $E000 dataset area, $F800 map
    buffer, RAM under I/O holding six pictures.
  - Identity: an address range together with what is loaded and the $01 bank
    bits. "$C000" alone identifies nothing.
  - Independent? No. This kind exists only relative to a configuration; I built
    build_mem() late and needed it for every overlay listing and xref.
  - Relationships: overlaps (NM1B at $B600 reaches $BFBF, over the $BB00 area;
    pictures overwrite the roster buffer); banking ($D000 I/O vs RAM copies of
    pictures).

  6. Code units: routines and the API

  - Examples: PRINT $0AC6, GETKEY $1955, LOAD_FILE $78B9, DRAW_PICTURE $4000,
    SET_MODE, LOAD_SPECIAL, the view builder in NM02, the 24 spell handlers, the
    bare-RTS stub at $19C8.
  - Identity: entry address within a memory context; for overlays the same
    address ($AE00) names different routines per file, so identity is (file,
    address). Jump-table entries are a second identity for the same routine
    ($0809 vs $0AC6) — a naming layer I generated automatically.
  - Independent? Primitives (text, keys, RNG, loader) yes. Game logic no —
    combat/spell code only made sense together with the tables it indexes.
  - Relationships: calls (via JT or direct — direct calls into the resident from
    overlays were an important discovery channel), reads/writes tables, uses
    zero-page variables, self-modifies operands (LDA #imm patched at $0C1A,
    $4F3B, $6431), is stubbed/replaced (crack).

  7. Variables and runtime state

  - Examples: $28/$29 position, $24 facing, $D4 mode, $E0 level/special type,
    $1E chain index, $D8 view depth, $2A key ready, $F8 loaded tileset, $2D
    loaded file, $0350–$036E view slots, $03B0/$03B8 encounter groups, $0380
    decimal accumulator.
  - Identity: address, but meaning drifts: $E0 is "dungeon level" in one path
    and "special-location type" in another; $78–$7B are a family of status flags
    I never fully separated.
  - Independent? No; meaning came only from readers/writers, and the emulator
    run was what settled some ($D8).
  - Relationships: shared between resident and overlays (the real "API" beyond
    the jump table); persisted into files (position, party).

  8. Records and tables (structured data)

  - Examples: 128-byte character record; 22×22 wall grid and flag grid; map
    header coordinate lists; 30×30 city grids; monster column arrays
    ($7D28/$7DA8/$7E28/$7EA8); item columns; spell stream + parallel tables;
    per-depth encounter mask/base; dispatch table $1B28; picture colour table
    $0D99; experience thresholds.
  - Identity: base address + element size + index space (monster id, item id,
    spell number, depth, class). Several tables share one index space — that
    shared index (e.g. "monster id 0..127") was the more useful identity than
    any address.
  - Independent? Partly: grids revealed themselves by histogram; column
    semantics needed code. The 5-bit packed stats and 12-digit decimal numbers
    were invisible without the unpack routines.
  - Relationships: indexed-by (index spaces), parallel-to (spell
    cost/flags/handler), points-to (name pointer tables, message pointers in
    maps), consumed-by (which routine).

  9. Formats (reusable encodings)

  - Examples: hi-bit ASCII with $DC and /-plural pairs; picture stream (E1/E2
    escapes, column-major interlace, animation deltas); map file layout; PRG
    header offset rule; RLE $9F; XOR checksum.
  - Identity: the rule itself, not a location; one format explains many
    instances (66 pictures, 16 maps, all strings).
  - Independent? Once derived from one reader, yes — and they were the most
    reusable knowledge in the project.
  - Relationships: instantiated-by units; derived-from a routine (the format's
    "authority" is the code that reads it).

  Two facts about reuse that matter:

  - Overlapping regions are used at different times, not simultaneously. NM1B
    (Guild) spans $B600–$BFBF, i.e. over the $BB00 dungeon-overlay area —
    harmless because it only runs in city mode. NMF0 spans $BB00–$C7FF, over
    both the dungeon-overlay area and the picture buffer — harmless because NM03
    loads it before the game starts, copies it away, and it is then
    overwritten. I established the ranges; I infer the "never simultaneously"
    from the control flow rather than from an exhaustive proof.
  - Loads clobber silently. LOAD_FILE has a one-entry cache ($2D = last file
    number) and nothing else. Showing a picture overwrites the roster copy in
    $C000; loading the roster overwrites the picture. The Guild code shows this:
    SHOW_PICTURE(0) first, then LOAD NM00/NM01 for a roster search, then the
    picture is stale (the emulator log shows exactly NM50, NM00, NM01, NM00 in
    sequence). Callers cope by simply reloading; the cache is what makes
    repeated SHOW_PICTURE of the same monster cheap.

  What an overlay load replaces and what stays

  Loading an overlay replaces only bytes in its own page range; the KERNAL LOAD
  is given an explicit address from the table, so the file's own PRG header is
  ignored. Everything in the "stable" table stays: the jump table, all resident
  routines, all resident tables, zero page, the party records, the text and
  picture windows' current contents, and whatever is loaded in the other
  reusable ranges. For example, loading NM1D (trap handler) into $BB00 does not
  touch the dungeon main loop at $AE00, the map at $F800, the tileset at $E000,
  or the party.

  The one real coupling is between the main overlay and its sub-overlays: NM02
  calls its sub-overlays with JSR $BB00 and expects them to return; NM09 does
  the same with JMP/JSR $B600. A main-mode switch (SET_MODE) reloads $AE00 and,
  for the city, $E000; it resets the stack (LDX #$FF; TXS) rather than
  returning, so the previous main overlay's state is abandoned. Mode 2 → 0
  (Utilities → city) additionally clears the party area (NM03 zeroes
  $CB00–$CE7F).

⏺ No — "overlay" was my working label for anything LOAD_FILE puts into a 
  reusable range, and that lumps together at least four different kinds. What
  they genuinely share is narrow; the differences are large.

  What all NMxx files have in common (established)

  - Same naming/loading path: number → "NM"+hex → KERNAL LOAD to a page from
    $796C; the PRG header is ignored and systematically wrong (-$8000 / -$D000),
    so the header is a build artefact, not a format field.
  - Same one-entry cache ($2D) and the same disk-prompt logic.
  - Size quantised to whole 256-byte pages minus one (n·256−1) for code files,
    or exact for data files — a first hint that they were produced by two
    different save procedures.
  - None is relocatable; all use absolute addresses into the resident and into
    each other.

  That is where the uniformity ends.

  Kind A — mode kernels: NM09 (city), NM02 (dungeon)

  - Format: raw code at $AE00, entry via JMP at $AE00 plus a tiny local jump
    table ($AE03…).
  - Code/data: code dominates; data is small tables tied to the world geometry
    (row tables 22·ns in NM02, 30·(29−ns) in NM09, view slot layout, the $AEEE
    remap, message strings for stairs/darkness).
  - Dependencies: heavy and bidirectional — they read map/city data by absolute
    address ($FC00…, $F800…), own the zero-page movement state, and host the
    kind-B/C scripts (JSR $B600/$BB00).
  - Lifetime: as long as the mode; replaced only by SET_MODE, which resets the
    stack rather than returning.
  - Trigger: mode change (boot → Utilities, Utilities → city,
    tavern/portal/tower → dungeon, stairs out → city).
    These are closer to "the second half of the kernel, swapped by world type"
    than to overlays.

  Kind B — location scripts (city buildings): NM0B–NM1B at $B600

  - Format: code + embedded text; no header; size up to 2496 bytes, mostly
    filling their pages (little detectable slack — each one's tail was
    different).
  - Code: menu loops; data: their own dialogue, prices/menus, name lists (8
    tavern names in NM0C, 8 temple names in NM0E).
  - Dependencies: party records, gold arithmetic, roster/stock files, SET_MODE;
    they also write position/facing on exit.
  - Lifetime: one building visit; return to NM09 or jump to a new mode.
  - Trigger: the city cell's special_type (cell>>3) through $1B28 (+$AEEE).

  Kind C — event scripts (dungeon squares): NM1C–NM44 at $BB00

  - Format: same as B but much smaller real content (100–470 bytes) with a
    shared slack template, i.e. saved from one long-lived buffer; several carry
    stale copies of other scripts' text (NM10↔NM0E, NM16↔NM11, NM13/19/1A share
    the magic-mouth text). Distinct provenance from kind B.
  - Code: one event each: text, riddle compare, item grant, scripted encounter
    setup, flag/position change.
  - Dependencies: map header flags (they clear one-time bits in the flag grid),
    encounter groups $03B0/$03B8, resident combat.
  - Lifetime: one square visit, always returns to NM02.
  - Trigger: map special-type at $FC30 or flag bit $10 (trap) → $1B28; some
    share numbers with kind B (types 23, 34–36, 42, 59 map to city files
    NM15–NM1A), so the same file is a B when reached from the city and a C when
    reached from a dungeon.

  - NM03 "Utilities" → a separate program that happens to be loaded through the
    same slot: it has its own font, keyboard matrix and 1541 block-command code,
    and its job (copy/format disks, start game) is outside the game loop. It
    also acts as the installer for the six under-I/O pictures.
  - NMF0 → an asset container, not code: 13 pages that are byte-for-byte the six
    picture files, loaded once at $BB00 and copied to $D000. Its "load address"
    is incidental.
  - NM04 and NM05–08 → data sets (facade/wall graphics, city grids, draw
    records) with four embedded pictures; $E000 is not an overlay slot, it is a
    data area chosen so it can sit under the KERNAL ROM.
  - NMA0–NMAF → level data; the map header is the closest thing to a "script"
    (coordinate lists selecting kind-C files).
  - NM00/NM01/NM0A → save files. They enter the picture only because $1B28[0] = 
    NM00 makes the Guild's roster load look like a special-type dispatch, and
    because they share the $C000 buffer with pictures.
  - NM50–NM90 → assets, sharing a slot but never executed.
  - NM10 (? command) → a command handler loaded through the location table with

  Consequences for the earlier picture

  - "Load address" is a property of the slot, not the file: $AE00, $B600, $BB00,

⏺ Symbols that were stable across the whole project

  These named things that exist in every memory configuration after boot, so one
  label file (labels_main.txt) served every listing:

  - Jump-table entries and their targets: J_PRINT/$0809→$0AC6,
    J_GETKEY/$080F→$1955, J_SHOW_PICTURE/$0803→$0D26, J_LOAD_FILE/$08C3→$78B9,
    J_SET_MODE/$0890→$19F0, J_LOAD_SPECIAL/$0884→$1B15. Two addresses per
    routine, but one meaning; every one of the ~60 overlay listings and the
    resident listing used them identically.
  - Resident tables: tbl_monster_name_ptr $8D0D, tbl_item_effect $A4F7,
    tbl_spell_cost $95B7, tbl_special_overlay $1B28, tbl_load_page $796C,
    tbl_line_lo/hi $C900/$CA00.
  - Resident buffers with fixed roles: PARTY_MEMBER1 $CB80, input_buf $0334,
    dec_accum $0380, enc_monster_id $03B0.
  - Most zero-page variables: cur_row $54, cur_col $55, str_ptr $58/59, rnd 
    $5A/5B, key_ready $2A, cur_file $2D, game_mode $D4, text_speed $88. Their
    readers and writers are resident routines with one job, so the meaning held
    everywhere.
  - Text-encoding facts ($DC newline, $AF plural) — not addresses, but symbols
    in the sense of conventions; valid in every file including maps and the
    intro.

  Symbols shared by several units but not universal

  - Slot names: OVERLAY_MAIN $AE00, OVERLAY_CITY $B600, OVERLAY_DUNG $BB00,
    PICBUF $C000, DATASET $E000, MAPBUF $F800. These name a role of a range,
    valid in all configurations, while the content behind them is not. I kept
    them in the shared label file deliberately because callers (JSR $BB00, JMP 
    $AE00) mean "whatever is loaded there".
  - Map-header fields: map_tileset_id $FC12, $FC00 level chain, $FC10 depth,
    $FC16 name, $FC20…$FD1F lists. Meaningful in every dungeon configuration
    (all 16 maps share the layout) and to both NM02 and the resident ($620E
    reads $FC12), but meaningless in city mode, where $FC00 is the second city
    grid.
  - City-grid symbols ($F800 special grid, $FC00 street grid): shared by NM09
    and NM10, invalid in dungeon mode.
  - Character-record offsets ($14 exp, $22 level, $30…$37 HP/SP, $38 class, $50
    items, $7F checksum): shared by the resident, NM1B, NM0B, NM0D, NM0E, NM17 —
    but they are offsets, applied through several base addresses ($CB80+,
    $CF00, $C800, $C000+128·n). The symbol is stable; the address it appears at
    is not.
  - Index spaces (monster id, item id, spell number, special type): the most
    stable identities in the project — an item id means the same thing in a
    roster file, a shop stock byte, a script's GIVE_ITEM, and the resident
    tables.

  Symbols meaningful in exactly one file

  - Every sub_Bxxx/L_Bxxx inside an overlay: sub_B19D (coordinate-list search)
    exists only while NM02 is loaded; sub_BB7C (XOR checksum) only in NM1B;
    D_B8F3/D_B909 (row tables) only in NM02; D_B13A/D_B158 (city row tables)
    only in NM09; D_AEEE remap only in NM09; D_B683 tileset colours only in
    NM02.

    NMA0 is loaded; the draw records at $E0A0 only for NM05–08; facade pointers

  - The intro's $4000-based names — a different program in a different memory
    image, sharing addresses with the resident game's $4000 picture renderer.

  Same address, different meanings

  - $AE00: NM09 city loop / NM02 dungeon loop / NM03 utilities entry.
  - $BB00: the dungeon event script or the start of the NMF0 picture container;
    $B600: any of 17 building scripts.
  - $C000: current picture, roster half 0 or 1, Garth's stock, or the tail of
    NMF0. $C0FF is a stock count in NM0D and a pixel byte otherwise.
  - $E000–$FFEF: city set vs. one of four dungeon sets; $F800: city grid row 0
    vs. map wall grid row 0; $FC00: street grid vs. map level chain; $ED00:
    pictures $5A–$5D in every set (a coincidental stable meaning inside an
    unstable range).
  - $D000–$DCFF: I/O registers when $01 has I/O on, six pictures when it is off
    — same address, same instant, different bank.
  - $0800–$0806: jump table, except after NM1B copies the reset stub there.
  - Zero page $E0: "dungeon level to load" in SET_MODE/ENTER_DUNGEON_LVL,
    "special-location type" in LOAD_SPECIAL; $28/$29: (ns,ew) in 22-wrap dungeon
    space vs. 30-wide city space; $42: "depth" for encounters vs. copied from
    $FC10.
  - Renamed by me as understanding changed: $456E PRINT_MSG_ID → SET_PIC_COLORS,
    $0D99 caption table → colour table, $FC20 "stairs" → special-event squares.
    Stale copies of the old names survived in generated files until
    regenerated.

  What I needed to know to resolve an address

  1. Which program image — game resident vs. intro vs. packer stage (three
     different $4000s, two different $0100s).
  2. Which slot occupants are loaded — mode ($D4), current main overlay, current
     sub-overlay, what is in $C000, $E000, $F800. In practice I resolved this
     from the file I was reading: a listing of NM02 implies NM02 at $AE00 and a
     map at $F800; but for the resident code alone this was often undecidable
     (resident routines that touch $FC12 or $C000 are valid under several
     occupants).
  3. The bank bits ($01) for $D000–$DFFF and for whether $E000+ reads are RAM.
  4. The base register/pointer for offsets — an offset like $38 is only a symbol
     relative to a record pointer (($0F),Y, ($6E),Y, ($2B),Y, $C800+).
  5. Which caller/path for polymorphic zero-page cells ($E0) — the meaning is
     per call site, not per address.
  6. Time in the boot sequence — $0810 was decruncher-loop code, then a new
     stage's entry; $C000 was screen init before it became the picture buffer.
  7. Occasionally execution evidence — $D8 (view depth) and $7A were only pinned
     down by poking them in the emulator; static reading gave the address but
     not a name I trusted.

  The practical consequence: my label mechanism (one flat file keyed by address,
  plus per-overlay files I never fully populated) could express 1 only by
  choosing which file to load, could express 2 only through slot-role names, and
  could not express 3–6 at all — which is why several "same address" cases were
  caught late or by luck.

  examples from the investigation: what made something belong to the group,     
  which memory configurations or files the group was useful in, whether groups

⏺ Yes — several, and they were of quite different natures. I'll describe them as
  they actually formed, roughly in the order they appeared.

  1. "The API" — the jump table and its primitives

  Formed on the first day, the moment I counted JSR $08xx across overlays.
  Membership: a routine belongs if it is reached through $0800–$08D1 or is one
  of the 34 direct-call targets overlays use. It came with its own sub-facts
  that travel together: calling conventions (X/Y string pointer, A =
  key/file/member), the zero-page cells each primitive consumes ($54/$55,
  $58/$59, $2A, $38), and the text-window geometry. Useful in every
  configuration; membership is intrinsic to the resident image. I applied the
  group as a unit by generating J_* labels from it and loading one label file
  into every listing.

  2. Text engine + encoding

  PRINT, PUTCHAR, NEWLINE, CAPTION, CLEAR_TEXT, the $DC/$AF/$FF rules, the
  window coordinates, the font, the line-address table. Belonged together
  because a change in my understanding of one (the /-plural rule) changed how
  every string dump in every file should be read. Useful everywhere, including
  maps and the intro, which use the same encoding without the same code.
  Overlaps with group 1 (the entries) and with the "picture" group (both need
  $C900).

  3. Loader facts

  LOAD_FILE, the page table, the disk-prompt tables, the $2D cache, the SAVE
  routine, the PRG-header offset rule, the disk membership of each file number.
  Intrinsic to the resident, but its consequence — "file N lives at address A" —
  is what I needed constantly, so the group turned into a module (btfiles.py)
  and every other tool depended on it. This was the group I most wanted to
  "apply together": as soon as it was established, every overlay listing had to
  be redone at the right address.

  4. Slot-occupancy sets (memory configurations)

  Not symbols but sets of loaded files: {NM09, NM04, one of NM0B–1B, something
  in $C000} for the city; {NM02, NMAx, NM05–08[set], maybe NM1C–44} for a
  dungeon; {NM03, NMF0} at boot. A symbol group was useful inside exactly one
  such set: the map-header names only inside the dungeon set, city grids only
  inside the city set. Membership is entirely load-dependent, and the sets
  overlap in their stable core (groups 1–3). I never wrote these sets down as
  first-class things; they lived implicitly in which files I passed to
  build_mem() and xrefs.py --files.

  5. Per-file symbol sets

  Every overlay's local labels (sub_B19D, D_B8F3, riddle answers, price lists)
  plus the facts about that file's slack and stale text. Intrinsic to the file,
  valid only when that file occupies its slot. Naturally disjoint between files
  that share a slot, but I wanted to keep them apart from the resident labels
  and largely failed (the shared label file leaked slot-role names into every
  listing, and overlay-local names never got their own files).

  6. Format groups (a reader routine + a layout + its instances)

  - Picture: $4000 renderer + $C000 stream rules + colour table $0D99 +
    SET_PIC_COLORS + the list of 66 files + the 10 resident copies. Membership:
    "explained by the same decoder". The colour facts joined late and forced a
    re-render of all instances — a group-wide update.
  - Map: NM02's movement/view/specials code + the $F800 layout + all 16 files +
    the flag-bit meanings + the coordinate-list idiom. Correcting the N/S bit
    order affected every member at once.
  - Character record: the offsets, the 5-bit stat packing, the 12-digit decimal
    numbers and their arithmetic routines, the checksum, plus four instance
    bases ($CB80+, $CF00, $C800, roster files). Overlaps heavily with the
    Guild/shop/temple scripts, which are its main writers.
  - Spell/item/monster tables: each is "one index space + parallel columns + a
    name-pointer table + the code that indexes it". The index space is the
    binding thing; it makes a roster item byte, a shop stock byte and a script's
    GIVE_ITEM constant members of the same group.
    These groups are intrinsic (they hold in any configuration where an instance
    is present) and they are where reuse actually happened.

  7. Dispatch/mapping groups ("glue")

  $1B28 + $AEEE + $1A5F + map special types + city cell types + the two disks'
  directories. Each row of these tables is an assertion of the form "type t
  means file f at slot s from disk d". I treated the whole set as one thing
  because each new row was worthless alone and the completed table explained 60
  files at once. Membership straddles resident data (the tables), map data (the
  type numbers), and files (the targets).

  8. Shared runtime-state families

  Position/facing/mode/level ($28/$29/$24/$D4/$E0/$1E), light/visibility
  ($78–$7B, $7A, $D8, $CD, $CE, $EC/$EB), encounter state ($03B0/$03B8/$8330…,
  $42), view slots ($0350–$036E). Members belong because the same routines set
  and test them together and because the scripts hand them across mode changes.
  Useful across resident + both mode kernels + scripts; membership intrinsic,
  but meaning per member sometimes path-dependent ($E0). The light family is the
  one I never finished as a group — I know its members but not its full
  semantics.

  9. Provenance groups

  "Saved from the same buffer" ($BB00 scripts with shared slack), "stale copy of
  X" (NM10/NM0E, NM16/NM11, NM13/19/1A), "duplicated asset" (NMF0 ↔ six
  pictures ↔ $D000; $ED00 pictures in five datasets; monster pictures on both
  disks), "developer residue" (symbol table, Applesoft), "older revision"
  (orphan ↔ NM02), "crack artefacts" (stub $19C8, /3532, separator entries).
  These cut across every other grouping: the $ED00 pictures are simultaneously
  members of the picture-format group and of each dataset file. Membership is
  intrinsic to the bytes and independent of loading, and this grouping was what
  let me discard material rather than analyse it.

  10. My own evidence groups

  Screenshots + emulator log + a script belong to the assertions they confirm
  ("loader order", "wall bits", "record columns"); the k-gram alignment belongs
  to the orphan; the histogram belongs to the wall encoding. I experienced these
  as attached to findings, not to addresses.

  Overlap and dependence, summarised

  - Groups 1–3 and 6 are intrinsic and configuration-independent; 4 and 5 are
    exactly the load-dependent layer; 7 is the bridge between them; 8 is
    intrinsic in membership but path-dependent in meaning; 9 is orthogonal to
    all of them.
  - Overlaps I kept tripping over: record offsets (6) inside scripts (5);
    slot-role names (4) inside the universal label file (1); colour facts
    belonging to pictures (6) but stored in resident code (1); map-type numbers
    belonging to maps (6) but decoded through resident tables (7).
  - The groups I most wanted to apply "together" were the ones where a
    correction propagated: text encoding, load addresses, wall bit order,
    picture colours, record HP/SP direction. Those are precisely the format and
    glue groups — and in each case the propagation was manual.
