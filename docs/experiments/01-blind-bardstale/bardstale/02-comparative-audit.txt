  1. Kinds of knowledge and technical entities the investigator actually needed

  Derived from what the code keys on, not from the retrospective's taxonomy:

  a. Storage containers and physical placement. d64.py models (image, track,
  sector), the BAM, directory entries (including deleted ones), chains with loop
  detection, and a usage map classifying every sector as file-owned / free /
  allocated-but-empty / data-without-owner. The last class was necessary because
  the investigation's first false alarm came from the 1541 fill pattern (4B 01 
  01…), which had to be hard-coded into the classifier (d64.py usage branch).
  The orphan chain T6S7→…→T5S18 is identified purely by its start sector and
  persisted as extracted/d2/orphan_T6S7.bin — a unit whose identity is a disk
  coordinate, not a name.

  b. Files as the program sees them. btfiles.py is the central abstraction: file
  identity is the hex file number (NM+hex), not the directory entry;
  file_path(n) searches both extracted disk directories, file_body(n) strips the
  PRG header, load_page(n) reproduces the loader's rule. Two sets DISK1/DISK2
  record which disk holds which number. Every later tool (disov, slack, xrefs,
  picture, dungeonmap, citymap, run_game) imports this module — the investigator
  explicitly did this "so every tool agrees on real addresses" (worklog §10).

  c. Program images and execution stages. unpack_main.py produces three 64 K
  images per program (main_stage1.mem, main.mem, intro.mem) plus .ranges files
  recording which addresses each stage wrote. Stage boundaries are detected by
  execution state (stop1: PC==$0810 and the byte there has changed to SEI), i.e.
  the entity "stage 2 code" exists only after stage 1 ran. The bug noted in
  worklog §5 (stop condition fired on the loop head; write attribution needed
  PC-after-fetch) shows that which instruction produced a byte was a needed
  fact.

  d. Memory configurations. btfiles.build_mem(files) = resident image + a list
  of file numbers placed at their real addresses. xrefs.py --files 02,09 and
  disov.py use it. run_game.py additionally models the $01 banking bits
  (io_visible()), keeps a separate 4 K I/O image, and logs every KERNAL LOAD
  with its destination — the configuration is reconstructed from the emulator
  log rather than stated up front.

  e. Code units and a two-level API. The 70-entry jump table at $0800 is treated
  as a first-class thing: xrefs.py --resident-entries seeds tracing from $C000,
  $0800, the IRQ vector, all JT targets and the contents of
  notes/direct_targets.txt — the 34 addresses overlays call directly, bypassing
  the table. labels_main.txt carries both names (J_PRINT $0809 and PRINT $0AC6)
  for one routine.

  f. Runtime variables (zero page, page 3). Needed constantly; encoded as label
  lines (002A key_ready, 00E0 dungeon_level) and, in run_game.py, as bare
  literals (mem[0x2A] for key injection, $28/$29/$24/$D4 in the print step,
  0x1955..0x19C0 for "idle in GETKEY").

  g. Structured data: records, grids, parallel column tables, index spaces.
  dungeonmap.parse() is a full record decoder (offset→field, coordinate lists
  terminated by $FF, pointer-relative strings via p-0xF800). The character
  record, monster/item/spell tables exist only as prose tables in 03_formats.md
  and as one-off dumps (items.txt etc.). The transcript's own analysis
  identifies that "the shared index (monster id 0..127) was the more useful
  identity than any address".

  h. Formats as reusable rules. Picture (picture.decode, whose loops "mirror the
  6502 code"), map, text encoding (strings_hi.ok() = 0xA0..0xFF, $DC newline),
  RLE $9F, slack template. Each format tool's docstring is the spec — the format
  knowledge is authoritative in code, with 03_formats.md pointing back to it
  ("see tools/picture.py docstring", "see tools/btfiles.py").

  i. Dispatch/glue tables. MODE_OVERLAY, SPECIAL_OVERLAY, RESIDENT_PICS, _D796C
  in btfiles.py; NAMES (type→building) in citymap.py. These are copies of
  resident tables lifted into Python so that other tools can use them as edges.

  j. Residue and provenance. slack.py defines slack statistically (majority byte
  per address across ≥3 files of the same slot, walk back until ≥90 % suffix
  match) and returns per-file (content_end, file_len); disov.py consumes that to
  clip the disassembly. Provenance facts (stale copies, Applesoft residue,
  orphan = older NM02) live only in notes.

  k. The investigator's own evidence artifacts. Screenshots, sheet*.png
  composites, the LOAD log, memory images, k-gram alignment results. Only the
  screenshots and images persisted; the alignment and the JT usage counts
  survive only as numbers quoted in 02_findings.md.

  2. How identity and location worked

  Every entity was keyed by one of the following, and the keys were converted by
  hand:

  Key used: (image, track, sector)
  Where: d64.py, orphan name
  Example: orphan_T6S7.bin, F-01 chain listing
  ────────────────────────────────────────
  Key used: file number (hex)
  Where: btfiles.py, all decoders, run_game LOAD hook (int(name[2:4],16))
  Example: NM1B, 0x1B
  ────────────────────────────────────────
  Key used: file offset
  Where: citymap.py (0x1800, 0x1C00), dungeonmap.py (0x400, 0x510)
  Example: docstring gives both: "$420 (FC20)"
  ────────────────────────────────────────
  Key used: runtime address
  Where: labels, listings, findings, xrefs
  Example: $FC12, $0D99
  ────────────────────────────────────────
  Key used: runtime address within a program image
  Where: separate .mem files; intro.asm vs main_traced.asm both contain a $4000
  Example: intro renderer vs game picture renderer
  ────────────────────────────────────────
  Key used: runtime address within a bank
  Where: run_game.rd_io
  Example: $D000 = I/O or picture RAM
  ────────────────────────────────────────
  Key used: element index in an index space
  Where: dump files, tables
  Example: monster id, item id, spell number, picture index (n-0x50), special
  type, level
  ────────────────────────────────────────
  Key used: offset relative to a base pointer
  Where: prose only (03_formats.md record table)
  Example: $38 class applies under ($0F),Y, ($6E),Y, $C800+, $C000+128·n
  ────────────────────────────────────────
  Key used: unit / finding ids
  Where: 01_units.md (U-ORPHAN, U-MAIN-JT), 02_findings.md (F-01…F-23)
  Example: referenced only from notes to notes

  The single biggest identity problem is visible in the tool code: the PRG 
  header address is wrong for most files (−$8000 / −$D000), so a file's address
  is not a property of the file but of the loader table. btfiles.load_addr()
  exists to override the header, and dis6502.py --prg (which trusts the header)
  was superseded by disov.py (which does not). Address conversions between file
  offset and runtime address are done ad hoc (p-0xF800 in dungeonmap, 0x1800 in
  citymap), and the transcript records slips from exactly this ("map offset $412
  ↔ $FC12, NM04 tail $F800 ↔ file 0x1800", "misread dump row offsets by $10
  once").

  Location was never a single object: the listing at disasm/nm02.asm:21 shows
  LDA $FC10 unlabeled, while labels_main.txt has FC12 map_tileset_id — the label
  set is one flat address→name map, so map-header fields are named only if
  someone happened to add that exact address, and the same address in city mode
  (street grid) cannot be given a different name.

  7. What context tools needed

  Each tool takes its context implicitly through arguments or hard-coding:

  - dis6502.py: --org, --prg, --entry, --data a-b, --labels FILE, --skip — the
    caller supplies address, entry points, forced data ranges and one label
    file. No notion of "which image / which bank".
  - disov.py XX [entries]: context = the file number; it infers slot group →
    slack analysis → content length → label files.
  - xrefs.py --files 02,09 --entry AE00 --range F800-FFFF --code-range …:
    context = a set of loaded files plus entry points plus the address window of
    interest. This is the most explicit "memory configuration" parameter in the
    toolkit, and it was needed because "raw byte scanning was useless" (worklog
    §15).
  - slack.py: context = the group of files sharing a slot (the template only
    makes sense per slot).
  - picture.py: context = the picture number (for the palette) — colour was
    "state set elsewhere" (worklog §11).
  - dungeonmap.py, citymap.py: context = file number and the fixed load base
    (0xF800 hard-coded in pointer resolution).
  - run_game.py: context = full machine state (bank bits, I/O image, IRQ
    cadence, loaded files log), plus a script of keys/waits/pokes. Several facts
    were only obtainable here: $D8 view depth, $7A light flag, loader order.
  - asmrange.py FILE START END: context = a listing file and an address window —
    a symptom that listings were being read in slices rather than queried.

  What no tool could be told: which bank $D000 is in for a static listing; which
  occupant of $C000/$E000/$F800 a resident routine is assuming; which call path
  gives $E0 its meaning (the listing at main_traced.asm:2298 shows LDX 
  dungeon_level ; X=$E0 special-location type — label and comment contradict
  because the context lives in the comment).

  8. How evidence and findings were represented

  - Findings (02_findings.md): numbered F-nn, each with Source (tool/command),
    Location, Evidence (prose: specific bytes, addresses, counts, strings,
    emulator log order), Description. Cross-references are textual ("See
    01_units.md U-ORPHAN", "(notes/items.txt)").
  - Units (01_units.md): U-* ids, a four-level status letter (D/P/I/?), "Indep."
    and "Needs" columns — an explicit attempt to record understandability and
    dependency per unit.
  - Formats (03_formats.md): offset tables with a "Sources:" line listing the
    routines each layout was derived from (e.g. character record: $124F, $43A6, 
    $104E, NM1B $B7A0-$B8B3, $71DC, $5170). Unknown fields are marked ? inline —
    the open-question queue is embedded in the tables.
  - Labels (labels_main.txt): ADDR NAME ; comment, with the comment carrying
    calling convention, side effects, and sometimes the evidence ("verified:
    26/32 roster records match").
  - Dependencies (04_dependencies.md): an ASCII arrow graph "A needs B" and a
    duplication table.
  - Visual evidence: screenshots composited into sheet*.png; contact sheet of
    pictures; rendered maps with in-image legends (dungeonmap.render writes
    name/depth/tileset/chain/exit onto the PNG; citymap.py writes a legend
    line).
  - Emulator evidence: F-16's evidence is a sequence (LOAD order, addresses)
    that came from Game.log, printed to the terminal and not saved.
  - Confidence is expressed lexically ("?", "probably", "inferred", "established
    from … confirmed by …", "Uncertain" sections in the transcript answers),
    never structurally.

  Evidence therefore attaches to findings as prose, with addresses as the only
  machine-checkable anchors; the transcript answer on groups states this
  directly ("I experienced these as attached to findings, not to addresses").

  9. Relationships encoded in tools versus in notes

  In code (executable, reused):
  - file number → disk, real address, body bytes (btfiles)
  - mode → main overlay; special type → sub-overlay (partial); picture →
    resident copy address (btfiles)
  - slot → member files (slack, disov)
  - file → content end (slack.analyse)
  - memory configuration → traced code set → references into a range (xrefs)
  - picture number → colour pair (picture.palette_for)
  - map file → fields, coordinate lists, pointer-resolved strings
    (dungeonmap.parse)
  - notes → tool: xrefs.py reads notes/direct_targets.txt; disov.py reads
    notes/labels_main.txt (+ optional per-overlay files). These are the only
    places where a note is machine-consumed.
  - execution stage → written ranges (unpack_main, .ranges)
  - KERNAL call → file load → log entry (run_game)

  In notes only (prose/tables):
  - record and column semantics (character record, monster/item/spell tables)
  - duplicate-of / stale-copy-of / older-revision-of (04_dependencies.md table,
    F-20)
  - unit → status / independence / needs (01_units.md)
  - finding → evidence → source tool
  - the "A needs B" derivation graph
  - open questions (? cells, "Uncertain" lists)
  - meaning of polymorphic variables per call path ($E0, $28/$29 in two
    coordinate systems)
  - the emulator hook list needed to run the game (F-16 prose, though also
    implicit in run_game.py)

  The asymmetry is telling: relationships that the investigator had to apply 
  repeatedly migrated into code; relationships that were concluded once stayed
  in prose — even when they were the ones later corrections invalidated.

  10. What would be difficult to preserve or integrate across independent 
  investigators

  1. Address keys are ambiguous without the investigator's head. A second
     investigator receiving labels_main.txt cannot tell that FC12 map_tileset_id
     is valid only when a map is loaded, that dungeon_level at $E0 is also the
     special type, or that $C000 PICBUF is sometimes the roster. The notes
     encode this in comments and the transcript, not in the label set.
  2. The file→address rule is a precondition for everything, but lives in one 
     module's constant. Any parallel investigator who trusted PRG headers would
     produce incompatible listings; merging would require re-basing every
     symbol.
  3. Tool constants are silent copies of the image. Three transcribed tables
     (_D796C, PIC_COLORS, SPECIAL_OVERLAY) carry no pointer back to their source
     address/version; one is already stale. Two investigators would each
     transcribe their own and diverge.
  4. Renames do not propagate. The PRINT_MSG_ID/SET_PIC_COLORS split shows that
     even a single investigator's own alias layer diverged; with two people,
     both names would circulate.
  5. Unreproducible dumps. items.txt, spells.txt, monster_names.txt, the JT
     usage counts and the k-gram alignment cannot be regenerated or checked by
     someone else; they would have to be trusted or redone.
  6. Slack/junk classification is a computed convention. slack.analyse
     thresholds (≥3 files, 90 % suffix match) define what "content" means for
     ~35 files; a different investigator's clipping would yield different
     content lengths and different "false targets" (the $2004/$2032/$1010/$1210
     entries in direct_targets.txt are exactly such artifacts, and it is not
     recorded which of the 34 direct targets are junk-derived).
  7. Evidence is narrative and tied to session state. F-16's confirmation
     depends on a run_game script that was not saved and on the LOAD log printed
     to the terminal; the emulator's $D8/$7A discoveries have no recorded
     probe.
  8. Provenance classes cut across every other grouping. "Stale copy of NM11
     inside NM16" is a relation between byte ranges of two files; nothing in the
     workspace can express "range X of file A is not content, explained by B"
     except a table row in 04_dependencies.md, so another investigator would
     rediscover (and re-scare themselves with) the same junk.
  9. Open questions are scattered as ? in tables, "unk408/unk411" field names in
     code, "(init 1, probably…)" in prose, and "Uncertain" lists in the
     transcript — with no shared index, they cannot be handed off or claimed.
  10. The unit inventory's status column is opinion at a point in time and
      already lags the tools (e.g. U-MAIN-3D marked P although the view builder
      was read for the map format).

  11. Abstractions implemented in code — the strongest evidence of need

  Ranked by how much the rest of the toolkit leans on them:

  1. btfiles.load_page/load_addr/file_body/build_mem — a

  Comparative audit: Bard's Tale evidence vs. re64 and re64-redesign

  Notation below: BT = the frozen Bard's Tale investigation; re64 = the
  implemented system in re64/ (docs + src/ + tests at the checked-out commit);

  1. The architectural model each version actually implements

  re64 (as built)

  Read from src/core/project/project.ts, src/core/claims/model.ts,
  src/core/project/loader.ts, src/core/memory/memory-map.ts, src/core/machine/,
  and the transport tests rather than from the prose:

  - Files/blobs: immutable content by hash, referenced by id; D64 members
    selected by directory name (file-source.ts, d64.ts).
  - Layers: dumb byte sources (prg, raw, bytes, rom) or symbols. A prg layer's
    address comes from its header; a raw/bytes layer declares one.
  - Targets: named, id-keyed, ordered lists of links (layer + optional at); the
    last link shadows; a target is the only thing a memory arrangement can be,
    and every address-bearing tool must be told which one (selectTarget, D1a). A
    flat 64 K MemoryMap is built per target; the platform symbol layer sits
    underneath; no banking model exists anywhere (memory-map.ts, machine/c64.ts:
    $D000–$DFFF is always the device bus).
  - Claims: one flat, id-keyed root; each carries at + frame (layer offset /
    target absolute / address absolute), optional extent, name, says
    (data/text/bitmap/jumptable/record), root, description, origin. Nothing
    resolves at rest; disagreements are reported, not resolved. Retirement is
    derived from evidence records and filtered in one place (loader.ts).
  - Declarations: constants, types (record layouts with fields, holes, arrays,
    bit units), decoders (sandboxed bytes → data), plus per-site bindings
    (labelUse, constantUse, primary).
  - Evidence: an entity about a claim (supports/refutes/retires, method,
    scenario, capture, other, note); provenance lives here, not on the claim.
  - Execution: run_program (flat memory, stop when control leaves
    supplied+written bytes, optional RAM capture saved as a .prg file with no
    provenance record), run_block, and scenarios (typed step lists;
    deterministic; prefix-checkpoint cache in memory only; captures persisted as
    entities with {scenario, step, kind, file}). No disk drive, no KERNAL call
    hooks, no $01 banking, no conditional stops beyond breakpoints/watchpoints.
  - Analysis: claim-independent decode graph, reachability from roots, blocks,
    effects, known-bits, xrefs, hygiene, disagreements(), findings()
    (code-in-claim / unreached / unexplained), coverage (find_undecoded).
  - Collaboration: Yjs document, per-session replicas, operation log, chat, undo
    — a large fraction of the codebase and of the contracts.

  The document is canonical; every listing, name, path, and report is derived on
  demand. The .re64 file is an export.

  re64-redesign (as described; no code)

  The RD keeps claims, types/records, bindings, constants, decoders, evidence,
  chat, CRDT, and the C64 focus, and changes the containment model:

  - Project ⊃ Program ⊃ Assets; a Machine state is machine state (memory incl. hidden
    banks, registers, devices, banking controls, cartridge, inserted media)

    byte-granular origin tracking; copy-on-write execution overlay; PLA mapping

  - Inclusion of another program's assets and knowledge as a pinned, read-only

  - Experiment / scenario / run / checkpoint / trigger / snippet / capture /

  - Claims with a subject that need not be an address (location, function,
    asset, program, relationship); asset-relative vs absolute coordinates;

  - Finds log (findings referencing claims/captures/etc. with per-reference

  Program (RD). Two observed problems that a Project + Machine states + claims do not
  settle cleanly:

  1. Scope for address-space facts narrower than the project. Zero-page and
     page-3 variables ($28/$29/$24/$D4/$E0/$2A/$0334/$0380) are true for every
     game configuration and false for the intro, which is a different program in
     the same project sharing $4000 and $0100. In re64 address-space claims
     travel to all targets; target-framed claims would need duplicating per
     target. Approximation: frame them on a 64 K image layer that is linked into

  4. Where re64 would have prevented concrete BT problems

  1. Stale rename (SET_PIC_COLORS in three listings vs. the notes): every
     listing is derived from one claim; editing by id changes all. (The alias
     claim at $08CC is a separate matter — see 2.10.)
  2. Overlay-local symbols never getting their own files: placed() frames a
     claim on the layer supplying its bytes by default, so sub_B19D is
     NM02-local without any decision by the investigator.
  3. Unit-inventory drift (01_units.md statuses): find_undecoded,
     unexplainedBytes, hygiene, describe_project are computed; nothing
     hand-maintained.
  4. Phantom call targets from slack ($2004, $2032 in direct_targets.txt): a
     data claim over the slack cannot stop control flow, but
     codeInClaim/unreached findings and warnings would surface the contradiction
     at the write, instead of it silently seeding xrefs.py.
  5. "Which bytes were these notes made against?": file hashes on layers;
     main.mem would be a captured file with a hash rather than a regenerated
     .mem.
  6. The colour-table / picture-palette regeneration (160 PNGs re-rendered by

     nothing is a stale artifact.
  7. Record-layout back-and-forth (worklog §14): a type with fields, holes and

  10. Method not recorded: method: read vs ran distinguishes F-06 (read) from

  whether by stored edges or by derivation is open (O6).

  R14. The distinction between statically read and observed-by-execution must be
  recorded per assertion.
  Evidence: F-16 confirms F-06/F-07/F-14 end-to-end; $D8/$7A established only by
  poking. re64 method satisfies this (E10).

  R15. Text in a program-specific encoding must be readable and searchable 
  without the investigator writing a scanner.
  Evidence: ASCII|$80 with $DC/$AF rules (F-13) in every file; strings_hi.py was
  the second tool written. re64 ascii renders ≥$80 as "." (c64/text.ts:132);
  EXP 10 decoded text by hand.

  R16. Operations over an asset's bytes independent of placement, and over many 
  memory states at once, must be possible.
  Evidence: slack.py, JT usage counts (F-05), per-file string dumps, k-gram
  alignment all ran over files; overlapping slots make a single all-overlays
  state impossible. Affordance level (T4).

  R17. Container-level structure (allocation map, deleted entries, chains not 
  named by the directory) must be inspectable and extractable.
  Evidence: F-01, F-02, F-20; the 4B 01 01… false alarm (WL §3). re64 d64.ts
  lists named entries only.

  2. Validated existing strengths

  Mechanisms that directly solved observed BT problems; a redesign should not
  lose them.

  S1. Layer-framed claims (Frame.layer, offsets stored, resolved per 
  arrangement). Solves R3 and the address-conversion slips ($412↔$FC12,
  0x1800↔$F800, WL/RN §1) by arithmetic. claims/model.ts, loader.ts
  (layerStart).

  S2. Per-site name binding (bind_name, labelUse). Expresses the path-dependent
  meaning of $E0 (dungeon level vs special type) that BT's flat label file could
  not (main_traced.asm:2298 label/comment contradiction). 06-algebra.md Shape
  2.

  S3. Derived rendering — nothing resolves at rest. Every listing/name/path is
  computed from the document; the stale-listing class (main_linear.asm
  unlabelled; SET_PIC_COLORS in some listings) cannot occur. B2;
  claims/listing.ts.

  S4. Claims cannot stop control flow; contested bytes get both readings; 
  codeInClaim/unreached/unexplained findings. Turns BT's slack-derived phantom
  targets into reported contradictions instead of silent seeds. B3, B5;
  claims/review.ts.

  S5. Record types with holes, bit-unit records, arrays with origin, preview 
  as:record, where paths. Directly the "record-layout table with per-field
  evidence" BT wished for (WL §14, R7). memory/type.ts.

  S6. Sandboxed stored decoders + render (grid/frames, PNG/APNG). Reproduces
  picture.py/dungeonmap.render as project-held, re-runnable, attributable

  S7. Evidence about a claim with method; retire vs refute vs remove. Satisfies

  S9. Typed, deterministic scenarios with prefix checkpoints. Matches the shape

  S10. Platform symbols and derived ROM effects. Subsume dis6502.C64_SYMS and

  S11. Roots as a field; find_unnamed ranked by references. The

  consumed by a tool.

  S12. Hygiene/disagreement reporting at the coarsest unit; coverage separated

  3. Concrete defects

  Correct regardless of architecture.

  X1. Relocating a prg layer keeps its header. projectForTarget sets address: 
  link.at; buildMemoryMap passes it as explicitStart; makeFileLoader returns the
  whole file with isPrg:false (src/core/project/file-source.ts:69–71).
  links.test.ts covers bytes layers only. Docs (05-model.md §3,
  decisions/machine.md) assert the general capability. Test to add: link a prg
  layer at another address and assert byte 0 equals the file's third byte.

  X2. D64 extraction is one byte long per file. extractFile takes nextSector
  bytes of the last sector instead of nextSector − 1 (src/core/c64/d64.ts).
  Verified on bardst-2.d64: nm02 3330 vs 3329, nm1c 1026 vs 1025. d64.test.ts
  bounds lengths within a range and cannot catch it.

  X3. D64 directory hides deleted entries and cannot start a chain from a 
  track/sector; no loop guard in extractFile. Blocks R17; a cyclic chain would
  hang.

  X4. Two capture paths with different provenance. Scenario captures are
  entities {scenario, step, kind, file}; run_program captures are bare file
  records with the run's wrote ranges only in the tool result
  (server/workspace.ts:1371–1505). R5 needs one rule.

  X5. Tool schema says address is "ignored for prg" (tools.ts:2662, 07-api.md)
  while the loader honours it (as a raw override) — inconsistent statements of
  one behaviour.

  X6. Documentation contradiction on Target.order ("a target list is a 
  history"). BT's configuration space is a lattice (resident × main overlay ×
  sub-overlay × buffer occupant), for which order has no meaning. The archive
  should gain the counter-example per its append-only rule.

  4. Open design decisions

  Requirements established; representation not. Each requirement is stated
  neutrally; alternatives follow.

  O1. Requirement (from R1, R5): a memory state must carry bank-selection and 
  device state alongside bytes, and analyses must take that state as input.
  Alternatives: (a) per-arrangement bank/device overlay on the existing target;
  (b) a machine-state object of which the byte arrangement is a derived view;
  (c) two objects — arrangement and machine state — with analyses accepting
  either.
  Discriminator: the three $D000 questions in decision D1.

  O2. Requirement (R4): knowledge must apply to a subset of memory states 
  without per-state re-entry, and must not appear in states where it is false.
  Alternatives: (a) a container entity owning assets and their claims; (b) an
  applicability condition on a claim ("holds wherever asset X is placed"); (c)
  convention: frame such claims on a whole-image asset linked into every
  relevant state.
  Discriminator: build game+intro under (b) and (c); count duplicated claims and
  claims shown where false.

  O3. Requirement (R2, R5, R16): the set of memory states an investigator reads 
  is large and mostly one-off; reading one must not require a document write for
  each.
  Evidence: dozens of build_mem/xrefs --files compositions vs four named ones;
  EXP 7/8 (target changes avoided; never named in 724 calls).
  Alternatives: (a) declared entities plus an inline composition parameter on
  reads; (b) base state + delta at query time; (c) states derived from execution
  checkpoints only.
  Discriminator: count reused vs one-off configurations in the BT transcript.

  O4. Requirement (R8, R9): entity indices shared across tables, and values that
  refer to assets/pictures/files/indices, must be representable so tools can 
  follow them and corrections propagate.
  Alternatives: (a) field reference types (index-into, enum, bitmask) with
  derived aggregation; (b) an index-space declaration that claims join; (c)
  stored relationship claims checked by hygiene against the bytes.
  Discriminator: encode monster columns + $1B28 under (a) and (c); count
  answerable queries and correction touch-points.

  O5. Requirement (R10): non-content byte ranges must be classifiable with a 
  reason, and coverage/decoding/search must respect the classification.
  Alternatives: (a) additional interpretation kinds with an "explained-by"
  reference; (b) a duplicate-of relation (under O4c); (c) asset-level provenance
  claims.
  Discriminator: mark the $BB00 template and one stale tail; check
  find_undecoded, find_bytes, and NM3F's disassembly.

  O6. Requirement (R11, R12, R13): composite findings, location-anchored 
  evidence, and discoverability of dependents after a correction.
  Alternatives: (a) a findings record referencing claims/captures/ranges (RD's
  proposal is one instance); (b) typed references on evidence (frame + range;
  tool run) without a new record; (c) derived-from edges between claims with a
  stale-dependents report — the merge argument that removed supersedes has not
  been tested for a non-ordering edge.
  Discriminator: re-encode F-01…F-23; apply the F-14 correction; count untouched
  dependents.

  O7. Requirement (R6): a run must be able to substitute for or emulate routines
  the model lacks, with the substitution recorded.
  Alternatives: (a) early-returning handlers at triggers; (b) drive/serial
  emulation with inserted media; (c) both, recorded as run conditions.
  Discriminator: script BT boot→cellar under (a); count steps, missing
  conditions, determinism.

  O8. Requirement (R15): program-specific text encodings must be usable by 
  preview, search, and listing.
  Alternatives: (a) extend the built-in encoding table with parameters; (b) let
  stored decoders serve as encodings; (c) decoders with declared external
  inputs.
  Discriminator: register a hi-bit decoder and attempt a text search.

  O9. Requirement (R5, R13-adjacent): observations produced by execution (values
  seen at cells, dynamic targets) must be retainable in a form static queries 
  can consult.
  Evidence: $D8, $7A (WL §17); RN §8–9; EXP 9 (captured SID data unused).
  Alternatives: (a) queryable access traces; (b) run-minted observation claims;
  (c) evidence notes only.
  Discriminator: trace the dungeon entry; check find_references $FC12 and
  call_graph $620E.

  O10. Requirement (R17): sector-level structure must be inspectable; whether a 
  chain is an asset kind is open.
  Alternatives: (a) tools over the image (BAM, usage map, extract by T/S →
  file); (b) chain as an asset kind carrying sector provenance.

  5. Unsupported hypotheses

  Concepts this experiment provides no evidence for or against. They may be
  justified elsewhere; do not cite Bard's Tale for them.

  H1. Inclusion of another program's knowledge as a pinned revision; 
  internalize; platform revisions. BT needed a fixed set of KERNAL/VIC names and
  nothing versioned.
  H2. Articles, editorial workflow, published editions. BT ended at a findings
  list.
  H3. Replicas, CRDT merge semantics, chat, per-session undo. Single
  investigator; BT shows only what would be hard to hand over (R3, R12, X4),
  which the id/frame/derivation mechanisms address.
  H4. Retire/refute preserving consulted-later wrong readings. BT shows
  corrections, not later consultation of superseded readings.
  H5. Shadowing as a presentation choice among overlapping knowledge. Mild BT
  instances ($0800 JT vs reset stub; $C000 init vs buffer); not enough to
  characterise.
  H6. Claims with non-address subjects in general. BT evidences specific
  subjects (asset ranges, indices, findings); not an open-ended subject model.
