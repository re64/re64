# Synchronization stress test

This independent assessment reads [purpose](../01-purpose.md), [architecture](../02-architecture.md), [synchronization](../07-synchronization.md), and the [document-model architecture review](document-model-architecture-review.md), in that order. [Machine](../04-machine-design.md), [knowledge](../05-knowledge-design.md), and [collaboration](../06-collaboration-and-interfaces.md) notes supply domain semantics. Architecture is the intended direction; candidate representations in the notes and assessment are not adopted decisions. There are no migration requirements.

The proposed maps, independent fields, atomic compound values, and tombstones handle the central editing cases. The most consequential remaining work concerns contribution-aware lifecycle undo and preservation of the context of retained results. Scenario execution and chat reconstruction need explicit ordering rules. These are different problems: unresolved scenario inputs can prevent a run without preventing synchronization, while chat ordering chiefly affects consistent reading. A bounded retry hazard also exists if the same creation command can initialize the same application ID independently on two replicas.

## Method and interpretation

Examples use conceptual field names, not a proposed schema. Unless stated otherwise, A, B, and C start with the same CRDT history, edit without receiving one another's new updates, and then exchange all updates. “After seeing” denotes a causal dependency; wall-clock time alone does not. A reference retains its ID even when its target is inactive. Every case distinguishes:

- **C — convergence:** equal accepted CRDT updates produce equivalent retained state, irrespective of delivery order and repetition.
- **S — structure:** values remain supported shapes and identifiable entities remain available where required.
- **M — meaning:** the merged state may require hygiene or may be unusable for a particular analysis.
- **I — intent:** independent contributions, reference meaning, and action/undo behavior survive to the extent promised; winning a register does not preserve every competing intention.

For cases using the proposed representation, convergence follows from applying the same Yjs updates to shared-history maps; domain outcomes below are reasoning about an adapter that has **not** been implemented or tested here. Reissuing a command, reconstructing JSON into new Yjs containers, and reapplying an existing binary update are different experiments. A convergent accepted subset does not excuse a receiver that chooses which valid edits to accept according to arrival order.

For each case, compare A-before-B and B-before-A delivery, repeat every update, and, where C appears, all six participant orders. Causally dependent updates may arrive early and must eventually integrate when their dependencies arrive. Compare retained fields and identities, lifecycle state, reference resolution, hygiene, analysis outcome, and reconstructed history—not merely visible JSON. Live chat order and pending local views intentionally need not match. The probes below execute permutations for three bounded library uncertainties; the rest are acceptance expectations, not claimed adapter test results.

## Case matrix

| Case and starting state | Participant operations | Expected merged result and assessment |
|---|---|---|
| **1. Independent and competing fields.** Type T has `name=Zone`, `description=old`. | A renames T to `ZoneRecord`; B changes its description to `200-byte entries`. In a separate trial, A/B/C set T's name to three different names; C remains disconnected until the others have exchanged updates. | **C/S:** independent trial retains both changes; competing trial retains exactly one name chosen by the CRDT. A later write after seeing all three supersedes that winner. **M:** a name winner is not agreement; duplicate names on different IDs remain possible. **I:** whole-entity replacement would wrongly reassert unrelated values. Undo targets contributions to the named fields; losing writes still need attribution/history even though they are not current values. Repetition does not add entities or history actions. |
| **2. Absence and null.** T has optional description `old` and required name. | A clears description; B renames T. Separately, A clears an optional nullable field while B sets meaningful null. | **C/S:** first trial retains the new name and explicit absence. Second selects either absence or null, preserving their distinction. Required-field clear is unsupported before mutation. **M:** neither state automatically denotes unknown machine state. **I:** undo must remember whether the prior state was absent, null, or a value; omission in an update cannot mean clear. |

Compound location replacement.** A note has asset-relative location `(asset X, offset 16)` and description `old`. | A replaces location with `(asset Y, offset 32)`; B replaces it with another supported location form; C edits description. Variant: A changes only the asset by constructing a full value, while B changes only the offset the same way. | **C/S:** one complete supported location plus C's description; no discriminator/payload mixture. In the variant, either complete replacement wins, so one participant's location intention is lost. **M:** asset, storage, and access-context forms still need definition; a structurally valid reference may be unavailable. **I:** undo treats location as one contribution, never repairs only its offset. Transactions across flattened keys would not provide this guarantee. |
| **4. Collection additions and creation retry.** T's field collection is shared; fields F and G do not exist. | A adds F; B adds G with the same name and offset; C adds H. A retries F's command after B has edited F. Exceptional trial: the same logical F creation is rerouted to a disconnected replica before it has received F's original CRDT initialization. | **C/S:** ordinary additions preserve F/G/H; duplicate names/offsets do not collapse IDs. An observed retry must leave B's edits intact and must not restore a tombstoned F. **M:** report competing field interpretations. **I:** one logical creation has one identity and attribution. The exceptional trial needs retry handling: local `if absent, create nested map` can hide an edited incarnation (probe P1). Random-ID collision is not the practical concern. Distinct intentional additions remain distinct even if content matches. |
| **5. Edit a type while editing its fields.** T is a 200-byte record with F at offset 0, length 20. | A reduces size to 100; B adds G at offset 160, length 40; C changes F's name. Each change is valid in its starting view. Variant: A changes T from record to another supported kind while B edits/adds record children. | **C/S:** ordinary trial retains size 100, F's rename, and G's identity. **M:** G no longer fits; flag it and prevent a decoder that requires a valid layout from silently reading beyond that layout. Inspection can continue. **I:** neither resizing nor undo should erase G. The kind-change trial depends on the unchosen ownership/value boundary: a complete kind-specific value can stay valid while old child identities are retained but inapplicable, or changing kind may require another definition identity. Independently editable discriminator/payload keys are insufficient. Replacing the whole child collection would lose independent edits. |
| **6. Delete, edit, and refer; then restore.** T and F are active; finding K exists. | A deletes T; disconnected B edits F and T; C adds K's reference to T/F. A later sees all updates and restores T. | **C/S:** before restoration, T is tombstoned with B's edits and C's reference intact; F is not recursively erased. After restoration, the same T has current retained fields. **M:** references through a deleted parent are inspectable problems, not malformed input. Whether active children appear in ordinary views while their parent is deleted needs an effective-visibility rule. **I:** restoration does not restore a snapshot, automatically endorse T, or reactivate a separately tombstoned F. |
| **7. Concurrent lifecycle writes.** T is deleted at all participants. | A restores T. B independently writes deletion again; C edits its description while offline. Variant: B first observes A's restore and then deletes. | **C/S:** concurrent trial selects one lifecycle value and retains C's description. C's edit never restores T. Causally later deletion wins in the variant. **M:** inactive targets remain resolvable. **I:** define whether explicitly deleting an already-deleted object emits a new lifecycle write or is a no-op; the result differs. An unseen concurrent deletion can defeat a restore, as the proposal already states. |
| **8. Undo creation; redo later.** A creates T. B has received T and edits it; C references T. | A incorporates those operations, undoes creation, then redoes it. Variant: another participant restores/deletes T between undo and redo. | **C/S:** ordinary sequence tombstones and then restores the same T, retaining B's edits and C's reference throughout. **M:** references temporarily resolve to a deleted entity; restoration does not validate the interpretation. **I:** initialization must never replay on redo. Peer edits/references alone do not forbid lifecycle undo under the proposal. The variant needs contribution-aware lifecycle reversal: a superseding lifecycle contribution must be identified separately from ordinary field edits. Raw UndoManager insertion reversal is not this operation. |
| **9. Grouped action, partial supersession, and redo.** T has old name/description. | A's single action changes both. B sees it and writes a new name. A receives B, undoes its action, then redoes it. C may update description between undo and redo. | **C/S:** undo preserves B's name and reverses A's description; P2 demonstrates this basic Yjs behavior. **I:** report name skipped/description reversed. Redo must not replay A's skipped name over B; if C superseded the reversal, redo of description also needs a skip/concurrency rule. The action remains one history group even if partly effective. **M:** independent surviving values can express an unintended combination; true coupling belongs inside one atomic value. See the separate offline undo counterexample below. |
| **10. Overlapping placements.** Machine configuration has no placements in a RAM range. | A adds P supplying byte `11`; B adds Q supplying `22` to the same backing range. Trial a: both priorities absent. Trial b: both 5. Trial c: P=10, Q=5. C adds a third overlapping placement R with absent priority. | **C/S:** all placement IDs survive every trial. **M:** a/b are ambiguous; c selects P until R introduces unresolved precedence. Analysis needing the affected bytes stops and identifies competitors; other ranges and asset reads remain usable. IDs or timestamps cannot choose bytes. **I:** no addition disappears because another placement overlaps. Missing priority is not implicitly zero. Overlap must concern the same backing storage; ROM and underlying RAM are not conflated merely because CPU addresses coincide. |
| **11. Concurrent priority edits.** P=10 and Q=5 overlap; P has description `old`. | A sets P=3; B sets P=8; C changes P's description. In another trial C deletes P. | **C/S:** exactly one P, priority either 3 or 8, plus C's independent edit or tombstone. **M:** with P active, Q wins if P=3 and P wins if P=8; the same merged state yields the same bytes. A concurrent independent Q priority change can produce a tie, which is ambiguity rather than a rejected merge. With P deleted, Q supplies the range, assuming no other competitor. **I:** priority edit cannot restore P; restoration later exposes its current retained priority, not necessarily its old precedence. |
| **12. Chat clocks and branches.** Message M has timestamp 100. | A sees M and adds N with predecessor M, timestamp 0 (clock skew). B adds independent Q at timestamp 50. C later sees Q and adds R with predecessor Q. Updates arrive in different orders and are duplicated. | **C/S:** one entity per message; predecessors persist. **M:** reopened history must put M before N and Q before R. A precise deterministic algorithm must settle remaining reading order; all replicas can then reproduce it. A simple timestamp sort fails. **I:** live arrival appends newly incorporated IDs without reshuffling, so live views legitimately differ. Duplicate delivery must not append duplicate messages. Tombstoning M must not sever M→N. A predecessor is not a receipt for all other visible messages. |
| **13. Chat missing or cyclic predecessors.** Only M is currently incorporated. | A incorporates N before N's independent predecessor entity P arrives. In a conditional variant where metadata edits are supported, A changes M's predecessor to N while B changes N's predecessor to M. | **C:** maps converge; late P eventually resolves the first gap. **S/M:** missing targets need an inspectable deterministic fallback. If predecessor edits are supported, locally valid edits can form a cycle; no reading order respects both edges. If predecessor is immutable and must name an already-seen message at creation, ordinary supported creation avoids this cycle, but import/invalid-input handling remains separate. **I:** define ordering metadata mutability and tombstone filtering before claiming stable reconstruction; a cycle fallback must not pretend to represent chronology. |
| **14. Scenario dependencies and action order.** Trigger/action definitions U and V have no dependencies; a small body is `[press fire, release fire]`. | A adds U-depends-on-V; B adds V-depends-on-U. Whole-body competition loses one inserted action but never fabricates a mixed body. **I:** if preserving independent action insertions is required, identity/dependency editing needs a different stated boundary. No shared-array requirement follows. |
| **15. Simultaneous scenario actions and deletion.** Two independent triggers can fire on cycle 20. | A configures U to write register A=0; B configures V to write A=1 at cycle 20. In another trial A deletes U while B adds a dependency on U. | **C/S:** both actions or the deleted-target reference survive. **M:** final register value cannot depend on map order. Define simultaneous-trigger semantics, dependency satisfaction, one-shot/repeat firing, and deleted-target behavior before executing this case. A run must use identified resolved input definitions; a later shared edit cannot silently alter a retained run's conditions. **I:** runtime-created/enabled triggers belong to that run, not automatically to the shared scenario. |
| **16. Retained results after correction/deletion.** R records a check of T.F at offset 160, scenario S, and claim C (`GOATS required`), under identified material and assumptions. | A changes F to offset 120 and revises S. C's author or a third participant deletes T/S after R is retained. | **C:** mutable objects and references can converge perfectly. **S:** tombstones retain identity, not automatically the old definition. **M/I:** R must still identify offset 160, the scenario/assertion actually examined, its inputs/assumptions, and output. It must not acquire revised support claims. This requires retained context or immutable revisions with explicit selection; current IDs plus tombstones alone fail. Historical inspection remains possible without rerunning R, while a new analysis may lack usable current inputs. Restoration of T/S does not change R's historical meaning. |

## Concrete counterexamples and their consequences

### Selective undo needs more than inverse assignments

Start with `x=0`. A writes `x=1`; B observes that and writes `x=2` while A is disconnected. A still sees 1 and implements undo as “if x equals my after-value, set x to 0.” B's write and A's inverse are concurrent. P3 produces a convergent final value of 0, overwriting B's superseding contribution. A local condition is not a distributed compare-and-set.

There is also a simpler fully incorporated case: A writes 1, then B knowingly writes 1 again. Equality cannot distinguish A's still-active contribution from B's replacement. Undo must not infer ownership from the number. P2's same-value variant leaves B's 1 intact with Yjs UndoManager.

The synchronization contract says undo affects the selected contribution and also recognizes concurrent lifecycle writes. It needs to state how those requirements interact for **unseen** supersession. Plausible alternatives include contribution-aware selective reversal, or explicitly scoped local eligibility followed by ordinary concurrent field arbitration with an accurately reported later outcome. The latter offers a weaker preservation guarantee; it cannot be described as preserving every unseen superseding write. A server-ordered eligibility decision is another possibility, with consequences for disconnected undo and incorporation policy. None is selected here.

Lifecycle reversal has an additional trap. Suppose A deletes T; B observes deletion and explicitly deletes T again. If that second operation constitutes a new contribution, blindly undoing A's deletion by clearing the marker overrides B. If repeated deletion is a no-op, there is no B lifecycle contribution to preserve. Both policies are plausible, but the adapter and history must agree about which happened. Creation undo must preserve the underlying entity regardless of the chosen selective mechanism.

### Validation of merged meaning can select winners by arrival

Case 5 starts with a 200-byte type. A shrinks it to 100 while B adds a field ending at 200. Both edits are locally valid. If a receiver rejects the second update whenever a field would exceed the current size, A-first preserves the shrink and rejects the addition; B-first preserves the addition and rejects the shrink. “All accepted updates converge” conceals an arrival-dependent accepted set.

Bounds, deleted targets, duplicate names, overlapping placements, and scenario cycles must be distinguished from malformed atomic values. The first group can result from supported edits and needs domain checks. A missing referent on a receiver may also simply reflect an update the receiver has not incorporated yet. Structural validation still matters, but must not accidentally impose serializable cross-object transactions on ordinary CRDT editing.

### Stable identity does not preserve a historical assertion

Retain a successful check of `T.F` at offset 160; move the same field to 120. Resolving R's reference to the current F now describes a check that never happened. Deleting and restoring T cannot repair this: restoration intentionally keeps current fields. Retaining Yjs deletion internals is likewise not an evidence-context contract.

Historical context must also cover a run's resolved configuration, selected claim meanings, relevant definitions, platform/material versions, and substantive unknown/default assumptions. A mutable pointer assembled after a long-running analysis finishes can already designate a different input from the one actually consumed. Choosing when inputs are fixed and retaining those actual inputs is necessary before promoting results to durable evidence, independently of the current-definition storage choice.

### Chat needs an algorithm, not a pairwise comparator

With M(time 100), N(time 0, predecessor M), and Q(time 50, independent), predecessor order demands M<N. Pairwise timestamp ordering of unrelated messages would demand N<Q and Q<M. These constraints form a cycle even though the predecessor graph is acyclic.

A deterministic topological traversal ordered by `(timestamp, ID)` among currently eligible messages yields Q,M,N. A branch-oriented traversal could yield M,N,Q. Both can respect predecessors; they express different interpretations of ordering independent branches. The current wording needs a precise choice, including timestamp normalization, missing predecessors, and filtering deleted nodes. It cannot require all unrelated pairs to obey timestamps while also always honoring predecessors. This is a presentation contract, not a reason to stop ordinary entity synchronization.

### Creation retry can construct competing containers under a bounded precondition

Ordinary random entity IDs and distinct additions are not a concern here. The exceptional precondition is that a command carrying the **same creation ID** can be retried through a replica which has not received the original initialization. A's first invocation creates nested map F and subsequent work edits it. B's rerouted retry sees no F and creates another nested map under that application ID. P1 shows one map wins and A's edit becomes inaccessible through normal F lookup. Replaying A's existing binary update does not cause this problem.

Checking for existence works when the replica already has the original entity, including a tombstoned one. If rerouting is allowed, alternatives include retaining/replaying the canonical creation update, deduplicating/routing the command through an authority with its recorded result, or an explicitly designed initialization scheme that cannot replace the original editable container. These have different disconnected-creation implications. The retry route must not manufacture a second initialization or a second history entry. This is bounded adapter/transport work, not evidence against random identity or maps in general.

### Transaction grouping cannot preserve every combined intention

A grouped edit that renames a type and changes its description can emerge with another writer's name and A's description. That is allowed independence, even if A preferred its combined wording. For a location discriminator and payload, the same mixing would be invalid and is correctly forbidden by an atomic value. For a scenario body, replacing the whole sequence preserves shape but may discard the other participant's inserted capture. Grouping alone solves none of these boundary choices. Action IDs must also survive transport splitting/batching so that a partially superseded action remains understandable as one intention.

## Necessary contract clarifications and model decisions

Priority reflects practical consequences, not a requirement to settle everything before development.

| Priority and affected work | Clarification or decision needed | Alternatives and boundary |
|---|---|---|
| **High: lifecycle and undo adapter.** Implementing undo/redo can otherwise hide entities or overwrite another contribution. | Specify effect identity, known versus unseen supersession, repeated delete/restore behavior, eligibility of redo after partial undo, and the observable result of skipped or later-defeated reversals. Separate immutable initialization from undoable lifecycle changes. | Contribution-aware reversal, explicitly weaker local eligibility plus concurrent arbitration, or coordinated eligibility need comparison. Preserve identity and references under every option. This gates those operations, not ordinary field editing. |
| **High: retained results/evidence.** A result could silently change meaning. | Choose retained-context or revision references; define when actual examination inputs are captured, dependency discovery, and how historical inputs and output remain available after edits/deletion/cache loss. | Evolving current definitions with retained context and immutable revisions with adoption remain open. Neither requires all ordinary definitions to become immutable. This gates trustworthy result retention. |
| **Before each model's supported edits.** Invalid compound values or destructive container replacement are avoidable. | Identify atomic boundaries, required/default/null/absent semantics, kind changes, child ownership, and parent-deletion visibility. Required creation structure must be available together even if a larger action is delivered incrementally. | Retain inapplicable children under the same parent versus use a new identity for a kind change; global versus parent-owned child lookup; exact reference forms remain model choices. Do not decide a full schema to close this report. |
| **Before receiver validation.** Valid edits must not be accepted by arrival order. | Separate malformed shapes from tolerated concurrent semantic states. Preserve references to deleted or not-yet-incorporated entities and provide meaningful statuses. | Staged validation can protect shapes, but bounds/precedence/reference checks need hygiene or execution eligibility. Keep action identity/attribution independent of transport packets and distinguish pending work from durability. |
| **Before scenario execution/editing promises.** Wrong action order changes the experiment. | Define dependencies, simultaneous firing, missing/deleted targets, cycles, repetition, and body edit granularity. Fix and retain actual run inputs rather than reading mutable definitions as execution proceeds unless live editing is explicitly chosen and recorded. | Atomic bodies lose one concurrent replacement; independently identified actions preserve additions but need execution relations. Graph-shaped definitions do not require a general workflow language. |
| **Before stable chat reconstruction.** Reading order otherwise differs across implementations. | Choose deterministic traversal, timestamp parsing/ties, missing-target and cycle treatment, metadata mutability, and when tombstones are hidden. | Eligible-node topological order and branch-based order have different results. Either can be deterministic with stated rules; live arrival remains local. This need not block other editing. |
| **Bounded: retry/reconnect adapter.** Relevant only if the command can be rerouted before initialization arrives. | Define durable idempotency identity, duplicate-command attribution, and the source of canonical CRDT initialization; retry must not reset or restore an entity. | Replay original updates, route/deduplicate requests, or prove an alternative initialization mechanism. Do not treat random-ID collision handling as the issue. |
| **Before machine composition consumes priorities.** This affects byte selection, not merge acceptance. | Specify priority value domain, absence, invalid numeric values, and deterministic reporting of tied/unknown precedence in the same backing storage. | The principal decision is already made: higher explicit priority wins only when a unique source is established; absent priority supplies no silent default. No ID fallback is needed. |

A decision about one feature should not become a universal development gate. Independent metadata edits, distinct-ID additions, complete atomic values, and basic tombstone storage can proceed under the stated rules while the affected historical, undo, ordering, and execution contracts are completed.

## Rules that survived the tests

1. Named-field patches preserve independent changes; a causally later register write supersedes what it saw, while concurrent selection is deterministic rather than wall-clock ordered.
2. Complete atomic locations prevent mixed discriminators and coordinates. The acknowledged cost is whole-value competition, including offset-only edits.
3. Stable entity identity separate from names, offsets, and display order preserves concurrent collection additions and makes collisions inspectable.
4. Tombstones separate lifecycle from content: concurrent edits and references survive deletion, restoration keeps current fields, and parent deletion need not erase children. This requires model-visible storage, not just Yjs internal history.
5. Semantic problems can remain synchronized: overlapping fields, incomplete references, unresolved applicability, and ambiguous placement precedence do not need a merge-resolution step.
6. Placement ambiguity is correctly local to analyses needing those bytes. Deterministic display ordering cannot substitute for a substantive configuration choice.
7. Maps are sufficient for the proposed membership collections. Chat reading order, record layout, and scenario execution each need their own stated semantics; none gains meaning from map insertion order.
8. Action grouping, CRDT merge boundaries, undo eligibility, durable attribution, and persistence acknowledgement are distinct responsibilities. Chat can remain attributed and durable while excluded from ordinary project undo.

The tests support the proposed shared building blocks. They do not establish that generic map operations or a library undo stack alone implement re64's lifecycle, execution, and evidence contracts.
