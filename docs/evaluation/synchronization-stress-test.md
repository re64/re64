# Synchronization stress test

This independent assessment reads [purpose](../01-purpose.md), [architecture](../02-architecture.md), [synchronization](../07-synchronization.md), and the [document-model architecture review](document-model-architecture-review.md), in that order. [Machine](../04-machine-design.md), [knowledge](../05-knowledge-design.md), and [collaboration](../06-collaboration-and-interfaces.md) notes supply domain semantics. Architecture is the intended direction; candidate representations in the notes and assessment are not adopted decisions. There are no migration requirements.

The proposed maps, independent fields, atomic compound values, and tombstones handle the central editing cases. The most consequential remaining work concerns contribution-aware lifecycle undo and preservation of the context of retained results. Scenario execution needs explicit ordering rules. The collaboration design now supplies a deterministic time-first chat view policy; it does not mandate that order for every view. These are different problems: unresolved scenario inputs can prevent a run without preventing synchronization, while chat ordering chiefly affects consistent reading.

## Method and interpretation

Examples use conceptual field names, not a proposed schema. Unless stated otherwise, A, B, and C start with the same CRDT history, edit without receiving one another's new updates, and then exchange all updates. “After seeing” denotes a causal dependency; wall-clock time alone does not. A reference retains its ID even when its target is inactive.

Local means one session's replica, including an MCP session hosted on the server
or a browser tab. Command checks and undo/redo records belong to that session;
shared CRDT updates and action history do not constitute a shared undo stack.
Receiving another session's edits or undo effects neither reexecutes its command
nor adds an entry to the receiver's undo/redo record. Local results below are
assessed against the initiating replica; merged outcomes are assessed after the
specified updates have been incorporated.

Every case distinguishes:

- **C — convergence:** equal accepted CRDT updates produce equivalent retained state, irrespective of delivery order and repetition.
- **S — structure:** values remain supported shapes and identifiable entities remain available where required.
- **M — meaning:** the merged state may require hygiene or may be unusable for a particular analysis.
- **I — intent:** independent contributions, reference meaning, and action/undo behavior survive to the extent promised; winning a register does not preserve every competing intention.

For cases using the proposed representation, convergence follows from applying the same Yjs updates to shared-history maps; domain outcomes below are reasoning about an adapter that has **not** been implemented or tested here. Replicas synchronize CRDT updates produced by local edits. Creation, editing, merging, and reconstruction use one admissible set of object states; there is no stricter creation-time state validator. A convergent accepted subset does not excuse a receiver that chooses which valid edits to accept according to arrival order.

For each case, compare A-before-B and B-before-A delivery, repeat every update, and, where C appears, all six participant orders. Causally dependent updates may arrive early and must eventually integrate when their dependencies arrive. Compare retained fields and identities, lifecycle state, reference resolution, hygiene, analysis outcome, and reconstructed history—not merely visible JSON. Live chat order and pending local views intentionally need not match. The probes below execute permutations for two bounded library uncertainties; the rest are acceptance expectations, not claimed adapter test results.

## Concrete counterexamples and their consequences

### Selective undo needs more than inverse assignments

Start with `x=0`. A writes `x=1`; B observes that and writes `x=2` while A is disconnected. A still sees 1 and implements undo as “if x equals my after-value, set x to 0.” B's write and A's inverse are concurrent. P2 produces a convergent final value of 0, overwriting B's superseding contribution. A local condition is not a distributed compare-and-set.

A fully incorporated case can also return to the same visible value through meaningful changes: A writes 1, then B writes 2 and subsequently 1. Each local operation changes the value, but the final 1 belongs to B. Equality with A's old after-value cannot identify the contribution to reverse. P1's changed-away-and-back variant leaves B's 1 intact with Yjs UndoManager.

The revised contract distinguishes incorporated supersession from unseen concurrent changes. Undo eligibility is evaluated in the initiating session's replica; its resulting edits merge normally with previously unseen updates. P2 therefore demonstrates a limit of the guarantee, not a contradiction in the current contract: a locally effective reversal does not promise a final value across replicas. Equality alone is still insufficient to identify an eligible contribution after incorporated changes, as the changed-away-and-back case shows. The adapter must implement this local eligibility, retained identity, and partial-reversal reporting consistently in UI and MCP; no coordinated eligibility decision or protection against every unseen write is required.

Repeated deletion of an entity already tombstoned in the initiating replica is a no-op and creates no undo step. Restoration of an already-active entity follows the same rule. This settles the repeated-command case without changing LWW merge semantics. Contribution-aware reversal of meaningful lifecycle changes remains necessary, and creation undo must always preserve the underlying identity.

### Validation of merged meaning can select winners by arrival

Case 5 starts with a 200-byte type. A shrinks it to 100 while B adds a field ending at 200. Both edits are locally valid. If a receiver rejects the second update whenever a field would exceed the current size, A-first preserves the shrink and rejects the addition; B-first preserves the addition and rejects the shrink. “All accepted updates converge” conceals an arrival-dependent accepted set.

Bounds, deleted targets, duplicate names, overlapping placements, and scenario cycles must be distinguished from malformed atomic values. The first group can result from supported edits and needs domain checks. A missing referent on a receiver may also simply reflect an update the receiver has not incorporated yet. Structural validation still matters, but must not accidentally impose serializable cross-object transactions on ordinary CRDT editing. The same resulting state must also be accepted when created directly. Creation cannot require an in-bounds field or an existing referent when supported edits and merges admit the opposite. Case 17 makes this explicit, including reconstruction of a tombstoned message with cleared content.

### Stable identity does not preserve a historical assertion

Retain a successful check of `T.F` at offset 160; move the same field to 120. Resolving R's reference to the current F now describes a check that never happened. Deleting and restoring T cannot repair this: restoration intentionally keeps current fields. Retaining Yjs deletion internals is likewise not an evidence-context contract.

Historical context must also cover a run's resolved configuration, selected claim meanings, relevant definitions, platform/material versions, and substantive unknown/default assumptions. A mutable pointer assembled after a long-running analysis finishes can already designate a different input from the one actually consumed. Choosing when inputs are fixed and retaining those actual inputs is necessary before promoting results to durable evidence, independently of the current-definition storage choice.

### Why the predecessor-aware view uses an ordering algorithm

With M(time 100), N(time 0, predecessor M), and Q(time 50, independent), predecessor order demands M<N. Pairwise timestamp ordering of unrelated messages would demand N<Q and Q<M. These constraints form a cycle even though the predecessor graph is acyclic.

The chat design now specifies a predecessor-aware view policy using a time-first scan with holding sets and a ready min-heap, yielding Q,M,N. Time-only or graph views remain legitimate alternatives; synchronization does not mandate a presentation order. This is equivalent to choosing the earliest ready message in a topological order. It respects the prepared predecessor links while preferring timestamps wherever possible, rather than requiring every unrelated pair to appear in timestamp order. Missing predecessors impose no constraint until incorporated; cycles have one deterministic link ignored in the view and remain reported. Tombstoned messages participate in ordering and are hidden only afterward. Recorded clock errors are not corrected: a far-future timestamp can delay a message and its successors in the reconstructed history. Live append still presents new arrivals immediately.

### Transaction grouping cannot preserve every combined intention

A grouped edit that renames a type and changes its description can emerge with another writer's name and A's description. That is allowed independence, even if A preferred its combined wording. For a location discriminator and payload, the same mixing would be invalid and is correctly forbidden by an atomic value. For a scenario body, replacing the whole sequence preserves shape but may discard the other participant's inserted capture. Grouping alone solves none of these boundary choices. Action IDs must also survive transport splitting/batching so that a partially superseded action remains understandable as one intention.

## Chat ordering design check

The standalone Python model in `/tmp/re64-chat-ordering-check.py` checks the
chosen algorithm independently of Yjs and any future UI implementation. It
passed 8,613 small graph/timestamp cases, covering every predecessor assignment
for up to four messages (including self-links, missing targets, and cycles),
with representative timestamp patterns including ties, reversal, and absence.
The ordering is compared with brute-force enumeration of all valid orders after
predecessor preparation, selecting the lexicographically earliest one by the
comparison key. That oracle shares predecessor preparation with the tested
algorithm; it independently checks ordering, not cycle detection. Reversed
input order and tombstone toggles were also checked. Forty permutations of the
concrete examples passed, as did iterative runs over a 100,000-message chain
and cycle. These checks support the algorithm's reasoning; they do not test
transport, live-view adoption, or an implemented re64 adapter.

## Rules that survived the tests

1. Named-field patches preserve independent changes; a causally later register write supersedes what it saw, while concurrent selection is deterministic rather than wall-clock ordered.
2. Complete atomic locations prevent mixed discriminators and coordinates. The acknowledged cost is whole-value competition, including offset-only edits.
3. Stable entity identity separate from names, offsets, and display order preserves concurrent additions with distinct IDs and makes conflicting names or offsets inspectable.
4. Tombstones separate lifecycle from content: concurrent edits and references survive deletion, and restoration keeps current fields. Parent/child links are ordinary ID references; hygiene identifies orphaned entities, which participants may tombstone. Garbage collection of tombstoned durable entities is disabled and deferred. This requires model-visible storage, not just Yjs internal history.
5. Semantic problems can remain synchronized: overlapping fields, incomplete references, unresolved applicability, and ambiguous placement precedence do not need a merge-resolution step.
6. Placement ambiguity is correctly local to analyses needing those bytes. Deterministic display ordering cannot substitute for a substantive configuration choice.
7. Maps are sufficient for the proposed membership collections. Chat reading order, record layout, and scenario execution each need their own stated semantics; none gains meaning from map insertion order.
8. Action grouping, CRDT merge boundaries, undo eligibility, durable attribution, and persistence acknowledgement are distinct responsibilities. Chat can remain attributed and durable while excluded from ordinary project undo.

9. Creation, editing, merging, and reconstruction share one admissible set of states. Cleared content, tombstones, and unresolved references are admitted under the same rules in every path; actual validators and adapters must verify the examples in case 17.

The tests support the proposed shared building blocks. They do not establish that generic map operations or a library undo stack alone implement re64's lifecycle, execution, and evidence contracts.


## Full reassessment — 2026-09-15

A separate review reread purpose, architecture, machine, collaboration, and
synchronization, consulting knowledge design for retained definitions. It
reassessed all 17 original cases plus new cases 18–19 against the revised rules.
No new architectural contradiction was found. This is a design reassessment,
not verification of an implemented re64 adapter.

Session-local command preconditions are distinct from admissible object states
and incorporation of incoming updates. Undo/redo records are session-local;
action history and effective reversal updates can be shared. Repeated local
lifecycle commands are no-ops, while meaningful changes follow LWW. Publication
is independent of connectivity and the most recent incoming merge.
